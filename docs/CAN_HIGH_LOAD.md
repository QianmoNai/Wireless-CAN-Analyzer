# CAN 高负载测试和使用边界

四种通信方式为 USB、Wi-Fi、BLE 和两台分析仪之间的 ESP-NOW。必须分别核对 CAN 源实际发送速率、接收的唯一序号、设备/App 丢弃和控制响应；界面显示的接收速率不能证明完整交付。

## 已测基线

2026-11-06，1 Mbps、标准 8 字节数据帧、近距离台架，Android 1.21.14、Linux 桌面 1.2.23、分析仪 1.24.7 显式实验 6 Mbps 构建。该构建开关只影响 ESP-NOW，正式默认仍关闭。下表是短时观察值，不能作为所有环境的无损上限。

| 方式 | 已测结果 | 当前使用取舍 |
| --- | --- | --- |
| USB | 生产通信层 7500 帧/秒档 60000 条全收；实际桌面 GUI 延长测试的 6000 档两轮各 180000 全收，7500 档两轮分别少 7/2 条 | 高负载原始帧记录优先使用，并监视丢弃计数；不能因通信层一次通过而声称 GUI 永久无损 |
| Wi-Fi | 桌面通信层和两端 GUI 的 2000 档全收；4000 及以上档发生设备转发丢弃 | 完整记录需求超出实测条件时切 USB；仅观察电机时可用已有电机详情模式减少原始流量 |
| BLE | 生产通信层 4000 档全收，但桌面 GUI 已少 117/32000、手机 GUI 少 7183/32000；2000 档均全收 | 手机原始流以实测较低负载为起点；提高负载时持续检查丢弃，或选择电机详情模式 |
| ESP-NOW 双机 | 原版双向各 100 帧/秒短测通过、各 200 失败；单向 500 档虽目的 CAN 全收，确认仍大量过期 | 转发前先减少源端非必要报文和查询；需要完整转发更高负载时，采用有足够带宽的有线连接。不能把过期命令排队很久后重放 |

原固件在桌面电机详情折中验证中，源实际约 7498 帧/秒、每轮 90000 条。BLE 明确设为 100/1000 Hz 时，设备采样 1201/12004 条与 App 实收完全一致，设备观测源帧数 90000，丢弃零；Wi-Fi 100 Hz 同样通过，1000 Hz 则设备 CAN 接收队列少 2 条。手机 Android1.21.14 随后的 BLE、Wi-Fi 各100/500/1000 Hz三档均通过：每档源90000帧、设备观察90000，采样与App实收一致，设备/App丢弃及CAN健康零。这些仅为各轮选定详情流的观察，更长时间仍须独立验证。

详情模式会明确选择电机及采样频率，适用于看参数和曲线。它不能替代全总线原始帧记录。页面 CAN ID 筛选和“暂停”只影响列表，不减少无线链路上的流量；缩小内存历史也不提高无线带宽。查询频率应按实际成功发送和反馈频率评估，设定 1000 Hz 不代表收到 1000 条反馈。

## 复测方法

使用 [STM32H723 台架](../fixtures/stm32-h723/README.md) 的双 CAN 构建、两条独立 CAN 总线和 OpenOCD。高负载源由 STM32 内部微秒时钟定频，载荷携带每轮 nonce 和连续序号；不使用主机逐帧 SWD 写入作为定频源。

- [单分析仪通信层测试](../scripts/test-can-load-hardware.py)：USB/BLE/Wi-Fi，逐帧位图检查，支持 `--probe-control` 测量已经停止的查询归属上的 stop-all 确认往返；不会发送电机运动命令。
- [双机物理测试](../scripts/test-dual-can-load-hardware.py)：双向独立 CAN 接收计数，单独核对无线确认和目的 CAN 交付。
- 实际桌面/手机还需独立验证接收、长历史、暂停/继续、筛选、详情、全屏及断线；通信层测试不代替 GUI 验收。

7500 档源实际约 7497 帧/秒。按每帧 111 位估算约 83.2%，未包含位填充、错误帧或失败尝试，因此不能写成精确实测的总线占用率。每轮都保留丢帧结果，停止压力源、恢复 USB/CAN 和周期模拟。优化前后对照与未采用的候选见 [性能记录](PERFORMANCE.md)。

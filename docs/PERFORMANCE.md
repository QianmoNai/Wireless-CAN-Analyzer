# 性能调整与测量

## 2026-11-05 CAN 模式实机优化（进行中）

台架为 STM32H723 模拟反馈，经物理 1 Mbit/s CAN 接入 ESP32-S3，再由 Linux 桌面接收。DJI 三个 ID 各 100 Hz、IMU 四类合计 400 Hz；高负载测试另外请求四个模拟达妙 ID 各 100 Hz 状态查询。实际查询成功频率约每 ID 95 Hz，不能将请求频率当作总线发送成功频率。没有发送使能或运动命令。

### 通信与调度

- BLE 增加可选批量通知 UUID 0006，保留每条 20 字节 v1 报文；旧 UUID 0003 兼容。批次按 MTU 限制，最多 200 字节，避免默认小包池的第二块链式分配。ACK/控制队列优先，批次收集和提交重试都有上限。普通高负载流仍可能丢弃，不能作为无损抓包链路。
- CAN owner 提高到优先级 6，避免被 TLS 任务饿死；Wi-Fi 的短等待至少一个 RTOS tick，修复 100 Hz tick 配置下 `pdMS_TO_TICKS(2)` 得到零而持续抢占的问题。
- CAN 的 TLS 批次上限为 64 条，UART 保持原批次配置。恢复 CAN 查询调度后，旧 16 条批次在 40 秒测试丢弃 28344 条；64 条诊断候选 30 秒设备丢弃为零。时长和候选不同，不据此计算精确改善倍率。
- USB/Wi-Fi 接收改为按块解析完整报文，并保留有界尾部。Wi-Fi 仅在连接阶段限次重试，可取消；证书不匹配不重试，不重放 CAN 指令。
- 本机有两个相同子网网卡。Linux 默认广播搜索会并行探测接口并合并重复结果；已保存设备连接根据 UDP 身份回应选择 socket 接口，不修改系统路由。TLS 仍先校验已保存证书，随后才发送认证信息。

生产非诊断固件使用 8 次提交后，另做主机同时打包条件下的各 60 秒复测：USB 收取 65232 RX / 23106 TX、设备丢弃 0，BLE 65208 / 22999、丢弃 10，Wi-Fi 65099 / 22742、丢弃 0；三路 CAN 错误、查询失败、连接错误均为零。该轮 ACK p95 分别 10.71/71.68/96.59 ms，Wi-Fi 自动选择 enp3s0。存在并行主机负载且无线结果有轮次变化，不能用这一轮宣称蓝牙已无损或计算固定改善比例。

后续独立长测：生产 BLE 无查询接收 300.15 秒，收取 209984 RX，设备计数增量 209538 RX，转发丢弃/CAN 错误增量为零，七路反馈最长主机静默 80 ms。这只代表该轮 700 RX/s 负载；较高负载仍可能丢弃。

Wi-Fi 在 wlan0 / 源 IPv4 192.168.1.119 的 180.47 秒四 ID 查询测试中，设备计数增加 192188 RX / 66832 TX、转发丢弃 2189、CAN 错误 0，一路查询租约失效。配置 ACK p95 103.69 ms、最大 1450.47 ms；TLS 最大阻塞约 1.343 秒，转发队列深度达到容量。已有 P0 的 `drop_*`/`lan_reject_*` 仅统计 UART 字节，CAN 模式下为零不能证明无丢弃；CAN 以 type4 状态计数为准。

同接口的 CAN 专用 TCP_NODELAY 候选在 73.75 秒连接重置、查询超时，丢弃 1370；CAN 会话关闭 Wi-Fi 省电的候选在台架复位后的 20.84 秒连接重置、查询超时，丢弃 43。两项均未通过稳定性门槛，`CAN_WIFI_CAN_TCP_NODELAY` 与 `CAN_WIFI_CAN_NO_PS` 保持默认 OFF，已恢复生产非诊断镜像。关闭省电候选的首次测试因事先发生 STM32 Bus-off 而失效，未计为性能对照。现有证据不能确定连接重置的底层原因。

恢复生产固件后，wlan0 同路径加主机 TCP_INFO 的目标 180 秒复测在 154.48 秒查询超时。末次可见设备增量 162809 RX / 57052 TX、丢弃/CAN 错误为零，但最后 2.222 秒全流无数据，不能推断缺少末尾状态的期间也无丢弃。成功配置 ACK p95 117.40 ms、最大 179.87 ms（不含最终未确认请求）；末次主机总重传 3、未确认/丢失计数各 1、拥塞窗口 1、RTO 2.016 秒，本地接收窗口约 1 MB，STM32 同期健康。TCP 指标是主机命令方向，现有证据尚不能定位 ESP32、无线或 AP 根因。测试失败已恢复 USB/CAN。

随后仅台架固定电脑接口 enp3s0 / 源 IPv4 192.168.1.131，相同生产固件、四 ID 各 100 Hz 查询运行 180.41 秒通过；设备增量 194193 RX / 68851 TX，丢弃/CAN 错误为零，配置 ACK p50/p95/max=68.15/83.96/118.48 ms，主机 TCP 总重传为零。主动七路最长主机静默约 96 ms，四路查询反馈最长约 350 ms，恢复 USB/CAN 成功。这是独立轮次，支持继续对照电脑路径，不能定位无线故障根因或证明有线转接路径长期无损；产品仍自动探测接口，没有修改系统路由。

### Android 手机接收与操作

Redmi K20 Pro / Android 11 经 ADB 安装独立包名的台架测试包，只有该测试包开启 WebView 调试。正式包保持原调试设置。手机目前实现 BLE/Wi-Fi，尚无 USB Host 接收路径，USB 实测仍在电脑进行。下列均使用真实手机、生产 1.24.3 固件和物理 CAN；电机/IMU 来自 STM32 模拟器，只发状态查询。

旧客户端只接收 UUID 0003 的 20 字节通知，未请求较大 MTU。六阶段各 15 秒测试时，设备累计转发丢弃从 129 增至 12063，App 丢弃和 JS 错误为零。1.21.1 优先订阅 UUID 0006，在 CCCD 之前串行请求 MTU 247；手机日志确认 MTU=247 和新 UUID，旧固件仍使用 0003。完整批次先验证再按 20 字节分派，防止尾部无效时部分交付控制响应。

批量接收加首页摘要修复后，六阶段各 15 秒通过，DJI/IMU/达妙详情收到 1500/1496/1339 个样本，App 丢弃、JS 错误和设备丢弃增量为零。设备旧累计 12925 不计入本轮增量。首页收到 mode=1 确认并稳定一秒后，观察 15 秒原始 RX 增量为零。两轮为独立连接，不能据此计算固定改善倍率，也不能宣称更高负载长期无损。

原生操作检查通过：温度双曲线横屏、页面无横向溢出、冻结曲线时采样继续、系统返回键恢复竖屏详情；进入后台会断开，回前台不会自动重开查询。Wi-Fi 数据测试复用电脑已认证身份，以私有测试配置传入并继续校验证书及令牌；这不覆盖手机 BLE 安全配对或配网流程。

手机默认网络路径的 Wi-Fi 连接在 TCP 建立后 TLS 握手超时；同一手机保留 VPN 设置，仅将设备 socket 绑定到同网段物理 Wi-Fi 后通过。另发现原 TLS 关闭在主线程触发真实 `NetworkOnMainThreadException` 闪退，不能把此前六阶段数据通过当作完整验收。现改为先终止底层 socket，再后台清理 TLS。修复后的 Wi-Fi 六阶段各 15 秒通过，详情 1495/1492/1458 样本，设备/App 丢弃增量及 JS 错误为零，首页额外原始 RX 为零，断开 0.057 秒且进程保留。

另定位到 UDP 发现长度错误：完整请求实际为 20 字节，原固件只接受截短的 19 字节。电脑实物查询验证旧镜像不响应 20 字节、响应 19 字节。Android 兼容发送两种长度后，在原固件、VPN 不变、UDP 仍走默认网络的条件下收到真实回应，因此没有增加 UDP 网络绑定。独立测试包仅把缓存 IP 改为失效地址 192.168.1.254，搜索得到真实 192.168.1.221 并通过完整六阶段与断开。随后固件修正为同时接受两种精确请求；烧录 production9 后实物验证两种长度均得到匹配身份回应。缓存列表项不计为新的发现响应。

随后 Wi-Fi 原生横屏、冻结、返回键和后台检查通过；连续 12 次完整连接/断开（含三次系统 Home 后台）及六次连接准备阶段取消也通过，同一 App PID 保持、没有自动重开查询。STM32 在这轮生命周期操作前后 CAN 接收命令数增量为零，fatal/rx_lost/bus_off/errors 均为零。前一次生命周期脚本误用依赖 rAF 的等待，在隐藏 WebView 上超时；即时读取已是断开状态，改为电脑端主动读取后完整重跑。以上为该手机及网络环境的独立轮次，不代表所有 Android/VPN 组合已验证。
